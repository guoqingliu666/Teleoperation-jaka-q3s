# V1.5 规划分片：保留已经检查完成的前缀

## 本次只读结果

最新日志 `readonly_20260927_133134_517136.jsonl` 共259段候选、4个Grip窗口，
出现一次312ms积压暂停和一次125ms累计规划超时。超时任务已检查42点，
调用64次IK，省去20次无效右端点调用。整次运动命令数0，结果仍为failed。
这些数据不能与上一轮不同的手柄轨迹直接换算速度提升倍数。

## 调整

过去只有整段完成或达到关节跨度限制，才交付已检查前缀。复杂路径可能在已有
大量有效前缀后仍触及120ms硬上限，导致结果整体丢弃。

现在采用60ms软交付时刻（原硬预算的一半）：下一轮若处于一个完整检查通过的
区间端点，则交付该前缀，由原有队列机制决定是否发送。中点、右端点、曲率、
关节余量等仍按现有规则完成检查；软时刻不是额外的运动授权。

- 没有通过完整区间时，继续检查，不能拿单个中点充当已验证路径。
- 正在处理已发现风险的细分分支时，不能因为时间到了就返回通过。
- SDK调用返回时超过120ms，仍丢弃迟到结果，即使已有较早前缀。
- 原始剩余目标、接收时间、Grip代次都保留；剩余路径仍需逐段厂商逆解。
- 300ms积压暂停、400ms硬过期及下发前许可检查保持有效。
- 未修改厂商队列深度、速度、加速度、姿态范围或伺服配置。

日志新增 `completion_reason=planning_slice`，只读会话汇总新增
`sampling_summary.planning_slice_plans`。它表示因计算预算交付前缀的次数，
不表示实机速度连续。分片可能增加运动段数量，实际接续效果仍需验证；
若长期输入超过消费能力，积压保护仍会生效。

## 离线验证

新增模拟慢逆解测试：交付点来自完整检查区间，返回的TCP等于最后检查点，
剩余目标的原始年龄不变；模拟已完成前缀后SDK突然阻塞，迟到结果仍被拒绝。
既有跳变、限位、曲率、松握、队列容量及下发前许可测试继续保留。

本轮未连接机器人、未发送运动命令、未发布GitHub。现场下一步仍使用②中的
“新轨迹只读测试”，无需改参数。复测结果需分别检查分片数、积压峰值和拒绝原因，
不能仅凭候选数量认定通过。
