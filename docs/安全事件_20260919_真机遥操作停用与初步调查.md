# 2026-09-19 真机六维遥操作涉险事件：停用与初步调查

## 当前结论（未完成根因分析）

用户报告：微小手柄动作伴随机械臂剧烈抖动、异常关节变化和去使能，JAKA 随后报警；现场险些发生事故。**本项目真机六维遥操作现已停用**。不得清除报警后重试、修改参数绕过锁定，或把离线单元测试通过当作真机安全验收。现场负责人和 JAKA 技术人员检查机器人、控制柜、电源/母线、J4 驱动与机械连接、控制器完整事件记录之前，不恢复本项目运动指令。

JAKA [S5 适用的 S 系列硬件手册 V09](https://www.jaka.com/profile/upload/2026/04/13/20260413154947A068.pdf)要求检查安全功能、末端工具和负载设置，并在抖动/失稳时采取停止措施；这些现场检查须由具备资格的人员按现场规程进行，不是由本程序远程代替。

本调查只读取既有日志和源代码；没有连接控制器、复位、上使能或发送运动指令。事故截图显示 `0x133220`（关节 4 伺服欠压）和 `0x10F000A`。JAKA [官方事件列表](https://www.jaka.com/zh/commonQuestion)将 `0x10F000A` 标为“机器人**退出**碰撞保护性停止”；它不是“进入保护性停止”的起因代码。需由完整控制器事件时间线确认究竟先发生了什么。

## 已确认的软件安全设计缺陷

1. **反馈过期仍允许目标排队。** GUI 使用 0.50 s 的机器人样本新鲜度门槛；在 250—327 ms 的 SDK 阻塞期间，仍记录了多帧 `actual_age_ms > 250` 的排队目标，直到超过门槛才暂停。这不是适合真机伺服的失效关闭时序。
2. **所谓“关节速度上限”没有约束实际执行轨迹。** 程序先以 JAKA `kine_inverse` 估算一个关节解并限幅，却只把笛卡尔目标交给 `servo_p`。最终由控制器内部执行，预估解与控制器实际选解不一定一致；该软件限幅不能称为真实关节硬限速。
3. **一个同步 SDK 工作进程混合伺服发送、逆解和遥测。** 代码名义上按 8 ms 发送 `servo_p`，但同一循环会执行阻塞的 SDK 查询和逆解；实测查询长达数百毫秒，因此无法保证 8 ms 伺服节拍。JAKA [SDK 简介](https://www.jaka.com/docs/guide/1.7.2/SDK/introduction.html)也提醒 Python SDK 的阻塞调用会卡住其它调用。
4. **未充分现场验证就开放了极限滑杆。** 厂家额定最大速度不是当前完整装配、场地和控制架构的安全设定值。这是本项目放行设计错误，不应归咎于操作者调节滑杆。

以上缺陷足以要求停用，但**不能据此单独认定** J4 欠压的电气根因，亦不能证明哪一帧命令导致最后的关节突变。速度前瞻滤波、控制器内逆解分支变化、供电/驱动异常、Tool 1 配置与负载参数等均需排查，不能靠软件猜测直接复机。
