# JAKA 连续段圆滑接口核查

## 已确认的厂商接口事实

本机 JAKA SDK V2.3.1 beta3 的 Windows C 头文件对 `linear_move_extend` 的 `tol` 参数写明：单位为毫米，通常视为与下一条运动之间的圆滑过渡圆弧半径。`tol=0` 对应精确到达点。因此，当前②在每段使用 `tol=0` 并等待 `is_in_pos` 后再发送下一段，必然表现为每段减速到停；这不是 Unity 丢帧造成的。

同一 SDK 的 `MotionStatus` 还定义了：

- `inpos`：当前运动命令是否完成；注释要求同时检查队列信息。
- `queue`：队列中的运动命令数。
- `active_queue`：正在进行圆滑融合的运动命令数。
- `queue_full`、`paused`、软限位、急停和碰撞状态。

本机 Python `jkrc.RC` 已离线确认包含 `linear_move_extend` 与 `get_motion_status`。这说明“使用厂商规划器做连续段圆滑”在接口层面有依据，不需要重新启用事故版本的逐周期 `servo_j/servo_p`。

## 尚未确认的内容

头文件没有充分说明 Python 返回字段顺序、允许的 `tol` 范围、队列容量、何时提交下一段、末段如何精确停止，以及 `motion_abort` 对圆滑队列的清空语义。任何一项都不能靠猜测直接进入真机连续遥操作。

新增 `Python/只读检查运动队列状态.py` 用来只读记录当前 Python SDK 的返回结构和耗时。它不接收手柄、不发运动，也不调用软件停止。

## 2026-09-24 本机只读结果

- 静止状态连续读取 20 次，均为 `inpos=1`、`queue=0`、`active_queue=0`，且队列未满、未暂停、无软限位/急停/碰撞。
- `get_motion_status` 中位耗时 2.85 ms，最大 7.78 ms；运动命令数为 0。
- 固定两段路径的厂商逆解只读预检通过：7 个采样点最大相邻关节变化 0.457°，相对起点最大关节变化 2.351°，距配置关节限位的最小余量 123.92°；运动命令数为 0。
- 随后的 5 mm + 5 mm 真机档执行两条命令并正常到位，末端位置误差约 0.06 mm，运动后队列为空且没有 SDK 报告的暂停、限位、急停或碰撞；操作者确认无抖动、异响和报警，但因动作太小，肉眼无法判断方向与拐角是否圆滑。
- 可视档 20 mm + 20 mm 已完成真机验收：两条厂商命令均送达；运行中 `max_queue=2`、`max_active_queue=1`，因此第二段确实在第一段执行期间进入厂商圆滑队列。末端终点误差约 0.043 mm；结束后连续 10 次只读均为 `inpos=1`、`queue=0`、`active_queue=0`，无暂停、限位、急停或碰撞。操作者确认方向正确、拐角连续无明显停顿，且无抖动、异响、报警。
- 24 mm + 24 mm 可视档也已完成真机验收：两条厂商命令均送达，运行中仍为 `max_queue=2`、`max_active_queue=1`；末端终点误差约 0.037 mm。结束后连续 10 次只读均停稳、队列为空且无 SDK 报告的暂停、限位、急停或碰撞；操作者再次确认方向正确、拐角连续无明显停顿、无抖动/异响/报警。
- 固定三段 `+Z20 → +X20 → -Z20` 已完成当前姿态的只读预检：31 个厂商逆解样本最大相邻关节变化 0.426°、相对起点最大关节变化 7.121°、距配置关节限位最小余量 102.227°；运动命令数为 0。

这些数据只说明当前静止状态和固定小路径的返回结构正常，不代表圆滑队列已经经过真机运动验收。

## 下一阶段门槛

1. 机械臂静止、无报警且没有其他 SDK 所有者时，运行一次只读队列状态检查。
2. 根据真实返回结构补充严格解析和“队列未知即拒绝”测试。
3. 50 mm 固定路径的只读预检已拒绝：首段累计关节变化会超过 12°；30 mm 在第二段同样被拒绝。因此新增 `--live-envelope-scan`：只读地逐毫米扫描当前姿态下固定 `+Z→+X` 两段路径，复用同一套厂商逆解与关节门槛，不发送运动。扫描结果决定下一档，而不是猜测段长。
4. 2026-09-24 的扫描结果为 5–26 mm 可接受、27–50 mm 因单段累计关节变化超过 12° 而拒绝，运动命令数为 0。下一真机候选档固定为 24 mm：不贴近 26 mm 边界，仍使用已通过的 10 mm/s、20 mm/s² 与首段 `tol=3 mm`。
5. 验收日志必须同时记录目标、实测 TCP、`queue`、`active_queue`、`inpos`、SDK 调用耗时和停止确认。
6. 该固定两段通过后，才讨论把离线前瞻采样点接入同一厂商队列；姿态、较大范围和较高速度仍是后续独立门槛。
7. 三段档必须先验证“补段时队列最多两条待执行命令”的实际返回；通过后才讨论把受限采样轨迹接入相同的补段机制。
8. 2026-09-24 三段档在最终监视阶段出现负队列数，严格解析器已拒绝继续并执行停止；后续三段动作锁住。须先用失败报告记录原始 SDK 返回，并与 JAKA 工程师确认该字段在圆滑队列中的有效语义，不能自行把负值解释为空闲。
