### 19:40 后的节拍、队列与 LPF 扫描结论

现场在无抖动、异响和保护停机的前提下继续了受限诊断。`step_num=2`、16 ms
发送周期下，LPF 截止频率 1.6/3.2/5/10 Hz 的 1 mm 往返结束残差依次约为
0.420/0.408/0.392/0.426 mm，没有随截止频率形成有意义的单调改善，因此停止
继续增大 LPF；问题不应解释为“截止频率太低”。

把 `step_num=2` 或 3 的插补时域与 8 ms 客户端更新周期拆开后，零位保持能通过，
但动态轨迹会排队：`step_num=3` 的 1 mm 往返发送 373 点后结束残差 0.927 mm，
接近规划峰值。该结果反证不能把较大的 `step_num` 当作 Windows/Python 通信抖动
的掩蔽手段；后续恢复 `step_num=1` 基线。

SDK 调用最大 9.112 ms，正常退出伺服。随后 1 mm 轨迹仍因本地旧门槛在一次
13.575 ms 调用后主动退出；当时 83 次队列返回仍全部为 1，净位移 0.393 mm，
不是完整往返结果。报告分别为
`Validation/sdk_servo_hold/servo_hold_20260921_195730.json` 和
`Validation/sdk_servo_single_axis/single_axis_1mm_20260921_200159.json`。

因此下一候选调度规则改为：固定 `step_num=1`；以厂商 `queue_num<=10` 为主队列
门槛；偶发慢调用后按绝对时间跳过最多 4 个过期小步，不追赶补发；每次真实相邻
下发目标再次检查关节差不超过 0.1°；单次通信空窗超过 32 ms 仍退出。该规则已
通过 13 项纯离线测试，但在现场人员再次确认上轮无异常前不继续真机运动。

## 本机计时器发现

本机 Conda Python 中 `time.monotonic()` 使用 `GetTickCount64()`，报告分辨率
15.625 ms；这比 SDK 的 8 ms 单步周期还粗。`time.perf_counter()` 使用
`QueryPerformanceCounter()`，报告分辨率 0.1 µs。新②候选与空载基准已统一
使用后者。旧真机程序不因这次离线工作而变更，故它的计时风险仍待处理。

## 对事故证据的直接约束
